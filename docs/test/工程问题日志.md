## Phase 1 — 环境搭建

### 2026-08-09 | 环境搭建 | docker compose up 启动时报 `Pool overlaps`，无法创建网络 | `db-diagnostic-agent_diagnostic-net` 占用了 `172.20.0.0/16` 子网，与 JeePay compose 配置冲突 | `docker network rm` 删除冲突网络后重试 | "Docker 多项目共存时子网冲突是常见问题，我会先查 `docker network inspect` 定位冲突源，再决定是删除闲置网络还是修改项目子网"

### 2026-08-09 | 环境搭建 | MySQL 容器 unhealthy，启动日志报 `ERROR 1062: Duplicate entry` | `init.sql` 是全量库快照，`patch.sql` 又重复插入相同主键数据；同时 `patch.sql` 尝试对已有列重复 `ALTER TABLE ADD COLUMN` | 临时注释 docker-compose.yml 中 patch.sql 的挂载，只跑 init.sql（完成后恢复 compose 文件） | "init.sql 和 patch.sql 的设计冲突是典型的数据库迁移问题——init 是全量 dump 但包含后续补丁的数据，导致增量式 patch 重复执行时主键冲突。排查时我先 `docker logs` 定位到 SQL 错误行，再确认两个脚本的数据覆盖关系"

### 2026-08-09 | 环境搭建 | `unable to prepare context: path jeepay-ui not found` | UI 前端代码在独立仓库 `jeepay-ui`，默认路径指向 `../jeepay-ui`，本地未 clone | 启动时只指定 7 个后端容器，跳过 3 个 UI 前端（API 测试不需要前端页面） | "前端仓库独立部署时，我判断后端测试不需要页面，用 `docker compose up 具体服务名` 精确控制启动范围，减少了不必要的依赖"

## Phase 2 — 支付模块

### 2026-08-10 | 支付模块 | Docker MySQL 密码错误导致连接失败 | 项目 docker-compose.yml 中 MySQL root 密码为 `rootroot`，测试配置误写为 `root` | 修改测试配置中的 MySQL 密码为 `rootroot` | "数据库连接失败时，先确认容器运行状态和端口映射，再核对 docker-compose.yml 中的实际密码，不凭记忆写配置"

### 2026-08-10 | 支付模块 | SignUtils 签名计算与服务端不一致 | SignUtils 在计算 MD5 签名时将 `sign` 字段也参与了运算，而服务端 `remove("sign")` 后计算，结果不一致 | 在 SignUtils 遍历参数时添加 `&& !"sign".equals(entry.getKey())` 跳过 sign 字段 | "签名验证是支付系统核心安全机制，client 和 server 的签名算法必须完全一致。排查时我先对比两边的签名结果，发现差异，再逐行对比代码找到字段过滤逻辑的差异"

### 2026-08-10 | 支付模块 | TestDataFactory 移除 sign 后重新计算时 sign 又被写回 | 工厂方法在删除 sign → 重新计算签名的过程中，对 params 的修改被再次引用，导致旧 sign 被写回 | 添加 guard：如果请求参数中已存在 sign 字段则跳过 | "数据工厂封装时要考虑参数不可变性——多次操作同一个 map 可能相互污染，加防御性检查可以避免"

### 2026-08-10 | 支付模块 | PAY-016 禁用商户测试失败 | `queryMchApp` 是 mchNo + appId 联合查询，MCH-DISABLED 商户使用默认测试应用查不到数据 | 为 MCH-DISABLED 新建专属应用 APP-FOR-DISABLED | "联合查询场景下修改单维度数据不够，需要确保关联维度也有对应数据"

### 2026-08-10 | 支付模块 | PAY-014/018 标记为死代码，无法触发预期错误 | Controller 层 `@NotBlank` 注解 + `queryMchApp` 联合查询在请求到达业务逻辑前就拦截了参数，部分参数缺失场景实际由 Spring 框架拦截而非业务代码处理 | 标记为废弃不测试，在用例清单中注明"死代码"理由 | "测试不能只看接口文档——框架层的校验（@NotBlank、@Valid）会先于业务层执行，导致某些'参数缺失'场景实际返回 400 的路径不同，需要源码确认"

### 2026-08-10 | 支付模块 | sign 字段 write-back 导致签名错误 | TestDataFactory 移除 sign 字段后重新计算 MD5，但操作顺序不当导致旧的 sign 值残留在 params 中 | 调整操作顺序：先移除 sign → 构建 query string → 计算 MD5 → 再设置新 sign | "签名计算的字段顺序和 inclusion/exclusion 逻辑是支付测试中最容易出错的地方"

## Phase 2 — 回调模块

### 2026-08-12 | 回调模块 | conf/devCommons 配置覆盖测试配置导致 DB 连接失败 | Maven pom.xml 将 `../conf/devCommons` 打包为 `classpath:/config/application.yml`，Spring Boot 中 `config/` 目录优先级高于根目录，覆盖了 `src/test/resources/application.yml` 的 datasource（端口 13306→3306，密码 rootroot→123） | 将测试配置从 `src/test/resources/application.yml` 移到 `src/test/resources/config/application.yml`，同路径下测试 resources 优先级更高，全面覆盖所有配置项 | 展示对 Spring Boot 配置加载优先级的理解，以及排查 classpath 冲突的定位能力

### 2026-08-12 | 回调模块 | FastJson 序列化导致响应 body 断言失败 | 项目使用 FastJsonHttpMessageConverter 替代 Jackson，字符串 body 被序列化为 JSON 格式（带双引号），`equalTo("success")` 实际需要匹配 `"\"success\""` | 改用 `extract().body().asString()` + JUnit `assertEquals` 直接比对，可在断言 message 中说明原因 | 展示对不同 JSON 序列化框架的理解，以及 RestAssured matcher vs 手动提取的取舍

### 2026-08-12 | 回调模块 | 测试用例执行顺序导致数据污染 | JUnit5 默认不保证 @Test 方法执行顺序，CB-02 先于 CB-01 执行，将 ING 订单状态改为 3，导致 CB-01 断言期望 2 实际为 3 | 在测试类中添加 @BeforeEach 方法，用 JdbcTemplate 直接 SQL 重置 ING 订单状态 | 展示对测试隔离原则的理解：每个用例独立，不依赖执行顺序

### 2026-08-12 | 回调模块 | @MockBean 与 SpringBeansUtil.getBean() 兼容性 | ChannelNoticeController 通过 `SpringBeansUtil.getBean(ifCode + "ChannelNoticeService")` 动态查找渠道服务，而非 @Autowired 注入。Mockito @MockBean 替换了 Spring 容器中的实例，getBean 返回 mock 对象，因此 mock 生效 | 验证通过，无需额外配置。关键理解：@MockBean 操作的是 Spring 容器级别，无论注入方式（@Autowired 或 getBean），拿到的都是同一个替换后的实例 | 展示对 Spring 容器和 Mockito MockBean 机制的理解，能解释动态 Bean 查找场景下 mock 为何仍然生效
