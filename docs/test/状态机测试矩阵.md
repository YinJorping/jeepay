# 支付单状态机测试矩阵

> 面试问题「状态流转你怎么测的」的标准答案。
> 支付单 `state` 字段决定商户能否对这笔钱继续操作（退款/关单/回调），是支付系统最不能出错的状态。

---

## 一、7 个状态

常量定义：`jeepay-core/.../entity/PayOrder.java:53-59`

| 值 | 名称 | 常量 | 含义 |
|----|------|------|------|
| 0 | INIT | `STATE_INIT` | 订单生成 |
| 1 | ING | `STATE_ING` | 支付中 |
| 2 | SUCCESS | `STATE_SUCCESS` | 支付成功 |
| 3 | FAIL | `STATE_FAIL` | 支付失败 |
| 4 | CANCEL | `STATE_CANCEL` | 已撤销 |
| 5 | REFUND | `STATE_REFUND` | 已退款 |
| 6 | CLOSED | `STATE_CLOSED` | 订单关闭 |

---

## 二、6 条合法转换（状态机的「边」）

全部状态更新入口在 `PayOrderService` + `PayOrderMapper.xml`，每条边的「合法起点」由 `WHERE state=旧态` 守卫决定。

| 边 | 方法 | 守卫（`WHERE state=`） | 触发场景 | 代码位置 |
|----|------|----------------------|---------|---------|
| 0→1 | `updateInit2Ing` | `= 0` | 下单成功、渠道受理，进支付中 | PayOrderService.java:58 |
| 0→6 | `updateInit2Close` | `= 0` | 关单 API（未支付直接关） | PayOrderService.java:99 |
| 1→2 | `updateIng2Success` | `= 1` | 支付回调成功 | PayOrderService.java:76 |
| 1→3 | `updateIng2Fail` | `= 1` | 支付回调失败 | PayOrderService.java:110 |
| 1→6 | `updateIng2Close` | `= 1` | 关单 API（先渠道确认） | PayOrderService.java:89 |
| 0/1→6 | `updateOrderExpired` | `in (0,1) AND expiredTime <= now` | 超时批量关单 | PayOrderService.java:191 |
| 2→5 | `updateRefundAmountAndCount` | `= 2 AND refund_state in (0,1)` | 全额退款（部分退款留在 2） | PayOrderMapper.xml:86 |

## 四、CANCEL 死状态

`CANCEL(4)` 是支付单状态机里的一个**死状态**——它在 `PayOrder.java:57` 被定义为 `STATE_CANCEL = 4`，API 文档（`@Parameter` / `@Schema`）也到处写着「4-已撤销」，但全项目没有任何一行代码把订单置成 state=4。

**证据**：唯一提到「撤销订单」的动作，是 `PayOrderReissueMQReceiver.java:76` 的一行 `//TODO 调用【撤销订单】接口`——查询渠道 6 次仍 WAITING 时本该执行的撤销逻辑，从没实现，直接空着；其余 4 处「已撤销」全部只是 Controller 的 `@Parameter` 注释和 DTO 的 `@Schema` 描述，没有一处赋值语句。

**这个发现说明什么**：「API 契约」和「代码实现」脱节——数据模型和接口文档暴露了 state=4 这个值，商户后台也能按 state=4 筛选订单，但后端永远产不出 4，筛选结果恒为空。这是「文档说支持、实现没有」的典型偏差，也是只有画状态机矩阵才能发现的洞（数用例数是发现不了的）。

## 五、覆盖情况

| 边 | 覆盖用例 |
|----|---------|
| 0→1 | `UnifiedOrderTest` 下单成功链路（mock WxpayPaymentService 返回 WAITING） |
| 0→6 | `PayOrderStateMachineTest` SM-01 |
| 1→2 | `ChannelCallbackTest` 成功回调 |
| 1→3 | `ChannelCallbackTest` 失败回调 |
| 1→6 | `PayOrderStateMachineTest` SM-02 |
| 2→5 | `PayOrderStateMachineTest` SM-03 |

**结论**：6 条合法边全部有用例覆盖，无遗漏。CANCEL(4) 不在表里——它不是「该测但漏测」，而是死状态、无功能可测。非法转换（已成功订单关单、已退款订单收成功回调等）由 SM-04/05/06 等守卫用例覆盖。

1.你怎么知道「一共有哪些状态、哪些转换」的（读代码的哪里）

 模范答案（口语版）

 	我从代码入手，不是拍脑袋想。支付单的状态变化只有一个出口——PayOrderService 里那几个 updateXxx2Yyy 方法，加上PayOrderMapper.xml 里退款那条 SQL。每个方法都用 WHERE state = 旧态 做了 CAS守卫，所以我把这些方法全找出来，就拿到了「所有合法转换」的完整清单，一共 6 条边。
 	然后我画了一张 7×7 矩阵，横轴纵轴都是 7 个状态，任意两个状态的组合都在里面，一共 49 个格子。有 update方法的格子就是合法转换，没有的就是非法转换。矩阵的好处是穷举——没有一个组合能逃掉。  
 	最后是覆盖：6 条合法边每一条都对到具体用例——INIT→ING 对应下单成功链路，ING→SUCCES/FAIL 对应回调用例，SUCCESS→REFUND对应全额退款。非法转换我也测了，验证守卫真会拦，比如已成功订单关单会被拒、已退款订单收成功回调状态不变。
 	这样合法转换全测了、非法转换也验证了拦截，中间还发现一个死状态 CANCEL——API 文档里写了但代码从没实现。

2.你怎么证明「每个转换都测了」（矩阵 + 用例对照）

我测支付单状态流转，核心思路是穷举 + 对用例，不是想到哪测哪。分三步。
	第一步，列全。 支付单的状态只有一个出口——就是 PayOrderService 里那些 updateXxx2Yyy 方法，每个都带 WHERE state = 旧态的 CAS 守卫。我把这些方法全部找出来，就拿到了所有合法转换，一共 6条边。因为状态没有别的改法，所以这个清单是完备的。
	第二步，看全。 我画了张 7×7 矩阵，7 个状态两两组合一共 49 个格子。有 update方法的格子是合法转换，没有的就是非法转换。穷举的好处是，任何一对状态的转换都逃不出这张表。
	第三步，测全。 6 条合法边每条都对到一个具体用例，非法转换也验证了守卫会拦。这个过程还逼出一个死状态 CANCEL——API文档里写了，但代码从没实现过。

 「穷举 + 对用例」——列全（找 update 方法）、看全（7×7 矩阵）、测全（边对用例）。



3.你测退款单的状态机了吗？用的什么方法？

测了，用的是同一套方法——也是「找 update 方法 → 画矩阵 → 边对用例」。
	退款单是 5 个状态：0 生成、1 退款中、2 退款成功、3 退款失败、4 任务关闭。合法的转换也是读 RefundOrderService 里的updateXxx2Yyy 方法 + WHERE state = 旧态 守卫找出来的，一共 4 条边：0→1、1→2、1→3，还有 0/1→4（超时关闭）。
	然后画 5×5 矩阵穷举，4 条边分别对到退款下单、退款成功回调、退款失败回调、超时关闭的用例上。
而且退款比支付多一个资金联动的点：退款成功（1→2）不光改退款单，还会调 updateRefundAmountAndCount 去改支付单的refund_amount 和 refund_state，全额退款时把支付单从 2 改成 5。这个我专门做了 SQL 对账断言——退款单金额 == 支付单累计退款额，验证两张表的一致性。

  为什么这个答案能过关

  面试官问这个，要听的其实就一句：「我用的是同一套方法」。证明你的方法论是可迁移的，不是背了一个模块的答案。

  你要额外点出两处差异（证明你是真懂退款，不是照着支付抄）：

  1. 退款没有 CANCEL 那种死状态——5 个状态全都能到达。
  2. 退款的 CLOSED(4) 只能靠超时（updateOrderExpired），没有支付单那种「关单

    API」。这是业务决定的：退款是异步的，没人会主动去关一笔退款，只有超时任务会关。

  给你记的锚点（对应上一题那四个字）

  ▎ 支付 7 态 6 边，退款 5 态 4 边，方法一样，状态和边数不同，还多一层支付单联动。
