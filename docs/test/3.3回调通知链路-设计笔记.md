## 一、3.3 与之前回调模块的区别

| | Phase 2 回调模块（已做） | Phase 3.3 回调+通知链路（本次） |
|---|---|---|
| 测的是 | **对内**：渠道回调 → JeePay 内部订单状态机转换（7 分支） | **对外**：订单状态更新后 → JeePay **通知商户**这条尾巴 |
| 触发方 | 支付渠道 → JeePay | JeePay → 商户 notifyUrl |
| 数据 | `t_pay_order.state` | `t_mch_notify_record` + MQ + HTTP 外呼 |

一句话：**之前测的是「内部状态」，3.3 测的是「对外通知」**——这条链路在现有 19+ 用例里从没被触发过（因为测试数据的 `notify_url` 全是空串，`payOrderNotify` 直接 return）。

## 二、完整链路（源码已确认）

```
渠道回调 ChannelNoticeController.doNotify
  └─ PayOrderProcessService.confirmSuccess            （订单 state 1→2）
       └─ PayMchNotifyService.payOrderNotify          （同步，请求线程内）
            ├─ notifyUrl 为空            → return（不通知）
            ├─ findByPayOrder 已存在      → return（幂等，不重复通知）
            ├─ createNotifyUrl            （拼商户 notifyUrl + MD5 签名）
            ├─ 建 MchNotifyRecord（state=ING=1, notifyCount=0, orderType=1）
            ├─ save()（duplicate 异常     → return，DB 兜底幂等）
            └─ mqSender.send(PayOrderMchNotifyMQ)
                 ↓ [RocketMQ 异步]
            PayOrderMchNotifyRocketMQReceiver
              └─ PayOrderMchNotifyMQReceiver.receive
                   ├─ getById 空或 state!=ING  → return
                   ├─ notifyCount >= limit      → return
                   ├─ HttpUtil.post 商户 notifyUrl
                   ├─ 返回 "SUCCESS"            → state=SUCCESS=2
                   ├─ 达到最大次数(6)           → state=FAIL=3
                   └─ 否则                       → 延迟 30s*count 重发 MQ
```

**关键文件（已读）**：
- `PayMchNotifyService.java:53` `payOrderNotify()` — 同步部分核心
- `PayOrderMchNotifyMQReceiver.java:53` `receive()` — 异步 HTTP 外呼部分
- `MchNotifyRecord.java` — `STATE_ING=1 / SUCCESS=2 / FAIL=3`，`TYPE_PAY_ORDER=1`

## 三、关键结论（面试可讲）

1. **商户通知幂等是两层**：同步层 `findByPayOrder` 已存在即 return；DB 层 `save()` 抛 duplicate 异常兜底。两层都防「重复回调导致商户被重复通知」。
2. **notifyUrl 来自统一下单请求**（`AbstractPayOrderController.java:263` `payOrder.setNotifyUrl(rq.getNotifyUrl())`），不是写死在配置里。
3. **商户通知是异步解耦的**：同步只落 `t_mch_notify_record` + 发 MQ；真正的 HTTP 外呼在 RocketMQ consumer 里做，失败按 30s/60s/90s…最多 6 次重试。
4. **通知 URL 带签名**（`createNotifyUrl` 拼 MD5 sign），商户侧可用同样算法验签防伪造。

## 四、风险识别

| 风险 | 后果 | 值得测吗 |
|------|------|---------|
| 重复回调 → 商户被通知两次 | 商户重复处理订单，可能重复发货/入账 | ✅ 核心 |
| notifyUrl 为空仍发通知 | 空指针/无意义外呼 | ✅ 边界 |
| 支付失败仍通知商户 | 商户误判订单成功 | ✅ 业务错误 |
| 通知记录没落库 / sign 缺失 | 商户无法对账、无法验签 | ✅ 数据正确性 |

## 五、用例设计方向（编号 + 场景 + 预期 + 风险理由）

> 测试方式：`@SpringBootTest` + `PaySpringTestBase`（RANDOM_PORT + JdbcTemplate 查 `t_mch_notify_record`）。

| 编号 | 场景 | 预期 | 风险理由 |
|------|------|------|---------|
| MCH-01 | 成功回调（ING→SUCCESS） | `t_mch_notify_record` 有 1 条，state=1(ING)、orderId=支付单ID、notifyUrl 含 sign、orderType=1 | 完整链路闭环：成功必须触发商户通知 |
| MCH-02 | 重复成功回调（同单发两次） | 通知记录仍 1 条（`count=1`） | 幂等：重复回调不能重复通知商户 |
| MCH-03 | 失败回调（ING→FAIL） | `t_mch_notify_record` 0 条 | 失败不应通知商户成功 |
| MCH-04 | 支付单 notifyUrl 为空，成功回调 | 0 条（订单仍 1→2，但不通知） | 空地址边界 |

> 关于「签名错误」：属**渠道回调的入站验签**，与商户通知是两码事；入站验签被 `wxpayChannelNoticeService.parseParams` mock 绕过，本阶段不强测（若要做，需单独走真实回调签名，优先级低）。

## 六、技术实现要点（重要，避免踩坑）

1. **必须 mock `IMQSender`**（`PayMchNotifyService` 里的 `mqSender`）：
   - 原因 A：不 mock 会真实发 MQ → RocketMQ consumer 真对 notifyUrl 做 `HttpUtil.post`，产生不可控外呼 + 后台改 `t_mch_notify_record.state`，污染测试。
   - 原因 B：mock 后可用 `Mockito.verify(mqSender, times(1)).send(...)` 把「通知已发出」变成显式断言。
2. **新增 `@MockBean` 要加到 `PaySpringTestBase`**（不能在新测试类里单独声明，否则生成第二个 Spring 上下文 → RocketMQ 冲突，这是之前踩过的坑）。
   - 需确认 `IMQSender` 是单实现（RocketMQ vender 下只有一个 `RocketMQSender`），按类型 `@MockBean` 应能消歧；若有多个实现再用 `name` 指定。
3. **测试数据**：新增 `prepare-mch-notify-data.sql`，支付单需带**非空 notifyUrl**（区别于现有全空串数据）。IDEM-01 的统一下单若走真实下单，`notifyUrl` 从请求体传入即可；回调类用例则预置 `t_pay_order` 带 notifyUrl + state=1(ING)。
4. **复用已有 mock 方法**：`PaySpringTestBase.mockParseParams` + `mockDoNoticeSuccess` / `mockDoNoticeFail`（已在回调模块验证可用）。
