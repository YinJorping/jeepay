## 6. 能理解客户流程

### 支付模块
- 统一下单 → MD5 签名 → 支付渠道 → 返回结果 的完整链路
- 订单 7 态：INIT(0) → ING(1) → SUCCESS(2)/FAIL(3)/CLOSED(6) → REFUND(5)

### 回调模块（最核心收获）
- 同步跳转（doReturn）vs 异步通知（doNotify）的触发方和流程差异
- 支付渠道 → JeePay 回调 → 订单状态更新 → 商户通知 的完整链路
- SQL WHERE state=1 守卫 = 幂等性 = 防重复/防非法状态转换
- doNotify 7 个分支：ifCode→查找Bean→解析参数→ID匹配→查订单→状态转换→后续处理
- 能画出完整流程图

### 退款模块（业务闭环第三步）
- 退款单 5 态状态机：INIT(0)→ING(1)→SUCCESS(2)/FAIL(3)，ING→CLOSED(4)，所有转换 CAS 守卫（`WHERE state=旧态`）
- 支付单退款三字段：refund_state（无/部分/全额）+ refund_amount（累计退款额）+ refund_times
- 核心校验：累计退款 + 本次 <= 支付金额（SQL 聚合 `sumSuccessRefundAmount` 防超退）
- 全额退款时支付单 state 2→5（已退款），部分退款 state 保持 2
- SQL 对账闭环：字段值 == 表 SUM 值，验证数据一致性

### 认证模块（双认证体系）
- 登录链路：验证码校验（第一道防线）→ Spring Security authenticate（loadUserByUsername 5 层状态校验）→ 菜单权限校验 → 生成 JWT
- 5 层登录拦截：密码错/用户不存在/用户禁用/商户禁用/商户不存在/无菜单，各自独立错误文案
- token 生命周期：JWT 只存 uid+cacheKey，用户详情在 Redis（TOKEN_{uid}_{uuid}，TTL 2h），每次请求滑动续签
- 鉴权失败两套通道：业务失败（HTTP 200 + code 9999）vs 认证失败（HTTP 401，Security entry point）
- 验证码一次性：登录成功后 Redis 删除 img_code_{token}

### 状态机完整性（Phase 3.1，横向铺开后的纵向收口）
- 支付单 7 态完整转换矩阵：6 条合法转换 + 6 条非法守卫，逐一有通过/拒绝用例
- 关键发现：`SUCCESS(2)→REFUND(5)` 是「纯 SQL 转换」（`PayOrderMapper.xml` updateRefundAmountAndCount），靠 MySQL SET 从左到右执行 + `CASE WHEN refund_amount+current>=amount` 联动，没有任何 Java 方法入口——全额退款同步把支付单 2→5
- 所有转换都是 CAS 守卫（`WHERE state=旧值`），改 0 行即转换失败——这就是幂等性/防重复的底层机制

### 幂等性（Phase 3.2，同一链路的纵向视角）
- 4 类幂等机制：统一下单/退款下单 = count(mchNo+业务单号) 去重；关单 = state 守卫；退款回调 = state=ING CAS（WHERE state=旧态，改 0 行即拦截）；支付回调 = state=1 CAS
- 关键语义：JeePay 幂等是 check-then-throw（重复请求返回 code=9999），不是「幂等返回原单」
- 核心资金安全点：退款回调 CAS 拦截后不执行 updateRefundAmountAndCount → refund_amount 不重复累加（否则超退）
- 下单成功链路：mock WxpayPaymentService.pay() 返回 WAITING → processChannelMsg 置订单 INIT→ING → 返回 code=0

### 对外通知链路（Phase 3.3，链路最后一条尾巴）
- 完整链路收口：渠道回调 → 订单状态更新（1→2/3）→ `PayMchNotifyService.payOrderNotify` → 落 `t_mch_notify_record`（state=ING）→ 发 MQ → consumer 异步 HTTP 外呼商户 notifyUrl（最多 6 次 30s 退避重试）
- 商户通知幂等是两层：同步层 `findByPayOrder` 已存在即 return；DB 层 `save()` 抛 duplicate 异常兜底（`Uni_OrderId_Type` 唯一键）——双层防「重复回调导致商户被重复通知」
- 通知 URL 带 MD5 签名（`createNotifyUrl` 拼 sign），商户侧可用同算法验签防伪造
- 异步解耦理解：同步只落库 + 发 MQ，真正的 HTTP 外呼在 RocketMQ consumer 里做，失败不阻塞订单主流程
- 发现并点亮「被空串短路的尾巴」：历史数据 notify_url 全空串导致 payOrderNotify 首行 return，这条链路从未被执行——测试设计要主动识别「测试数据把代码分支短路」的盲区
