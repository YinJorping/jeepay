## Phase 2：模块测试循环 🔄

这是整个项目的核心。以后每个模块都走同一条流程：

```
测试需求 ──→ 这个模块做什么？核心接口/核心状态是什么？
    ↓
业务理解 ──→ 谁用？什么流程？什么规则？数据怎么流转？
    ↓
源码分析 ──→ Controller → Service → Mapper → DB，理解调用链和关键判断
    ↓
风险识别 ──→ 哪些地方最容易出错？哪些是业务不能接受的？
    ↓
用例设计 ──→ 先写用例清单（编号+场景+预期结果），不写代码
    ↓
自动化实现 ──→ JUnit5 + REST Assured + SQL 验证
    ↓
执行分析 ──→ 跑了多少条？通过率？失败根因？
    ↓
工程沉淀 ──→ 用例清单更新、问题日志更新、commit
```

## Phase 3：核心业务专项测试

模块循环完成后，针对三个高价值场景做深入测试。

### 3.1 状态机完整性 ✅

覆盖支付订单 7 个状态之间的合法/非法转换：

```
INIT(0) → ING(1) → SUCCESS(2) → REFUND(5)
                  ↘ FAIL(3)
INIT(0) → CLOSED(6)
```

对每个合法转换写一个通过用例，对每个非法转换写一个拒绝用例。

**已完成产出（6/6 用例通过）**：
- `PayOrderStateMachineTest`（SM-01~SM-06），补上模块循环阶段漏掉的转换
- 合法转换：INIT→CLOSED、ING→CLOSED（mock 渠道确认）、SUCCESS→REFUND 全额退款（纯 SQL 转换，核心）
- 非法守卫：INIT/REFUND 收到成功回调状态不变、SUCCESS 关单被拒
- 前置重构：合并 `CallbackTestBase` + `RefundSpringTestBase` → 单一 `PaySpringTestBase`，全模块共享唯一 Spring 上下文，为 Phase 4 `mvn test` 一键全量扫清障碍
- 测试数据：`prepare-state-machine-data.sql`（5 条不同状态订单）

### 3.2 幂等性 ✅

重点场景：重复支付请求、重复回调、重复关闭订单、重复退款。

验证：订单状态不变、金额不变、数据库只一条记录、不能因为重复请求产生错误的业务结果。

**已完成产出（4/4 用例通过）**：
- `PayOrderIdempotencyTest`（IDEM-01~IDEM-04），补上模块循环阶段漏掉的幂等缺口
- 4 类幂等机制逐一验证：重复统一下单（count 去重）、重复关单（state 守卫 + 渠道只调 1 次）、重复退款回调（state=ING CAS，refund_amount 不重复累加，核心资金安全）、重复退款下单（count 去重）
- 关键结论：JeePay 幂等语义是 check-then-throw（重复请求返回 code=9999），而非「幂等返回原单」
- 顺带修复 2 个 Phase 2 遗留失败：testCloseOrder 数据污染（补复位）、testNormalOrder 假渠道参数（mock WxpayPaymentService 测下单成功链路）
- 测试数据：`prepare-idempotency-data.sql`（4 条支付单 + 2 条退款单）

### 3.3 回调 + 通知链路 ✅

形成完整链路：模拟支付渠道 → 支付结果 → JeePay 回调 → 订单状态更新 → 商户通知。

**已完成产出（4/4 用例通过）**：
- `PayOrderMchNotifyTest`（MCH-01~MCH-04），点亮此前从未被触发的「对外通知」尾巴（历史数据 notify_url 全空串，payOrderNotify 首行即 return）
- 4 类通知场景：成功回调生成通知记录（state=ING、带 sign、orderType=1）、重复回调幂等（仍 1 条）、失败回调不通知、空 notify_url 不通知
- 关键机制：两层幂等（同步 `findByPayOrder` 已存在即 return + DB `save()` duplicate 异常兜底）；通知异步解耦（同步只落 `t_mch_notify_record` + 发 MQ，HTTP 外呼在 RocketMQ consumer，最多 6 次退避重试）
- 新增 `@MockBean IMQSender` 到 `PaySpringTestBase`：确认 4 个 IMQSender 实现靠 `@ConditionalOnProperty(isys.mq.vender)` 只激活 RocketMQSender，按类型 mock 可消歧；mock 后既阻断真实外呼又可用 `verify` 断言「通知已发出」
- 测试数据：`prepare-mch-notify-data.sql`（4 条带非空 notify_url 的支付中订单）

**2. 本地一键脚本 `scripts/run-tests.sh`**
- 三步：校验 Docker 容器 → 幂等加载 `docs/test/prepare-*.sql` → `mvn -pl jeepay-payment,jeepay-merchant -am test`
- 全量 84 用例（支付 62 + 认证 22）一键跑通

**3. GitHub Actions 流水线 `.github/workflows/ci.yml`**
- 新增 `integration-test` job：复用 docker-compose.yml 起 MySQL/Redis/RocketMQ 四依赖 → 加载 seed → `mvn test` → 上传 surefire 报告
- ⚠️ 待验证：当前 origin 是上游 `jeequan/jeepay` 而非个人 fork，需 fork 后推分支才能触发 CI

**迁移过程中暴露并修复的 2 个真实问题（详见工程问题日志）**：
- seed 非幂等：`t_sys_user_auth` 自增主键无唯一键，重复加载累积重复行 → selectOne 抛 TooManyResultsException
- 断言漂移：缓存启用后「商户不存在」分支被 appId 缓存预热态改变，改用永不存在的 appId 保证确定性

### CI 流水线

```
代码提交 → 编译 → 自动化测试 → 测试报告 → 失败反馈
```

用 GitHub Actions，MySQL service container + `mvn test` + 报告上传。

### 一键运行

确保 `mvn test` 一键跑全部用例，无需手动启动 Docker、无需手动初始化数据。
